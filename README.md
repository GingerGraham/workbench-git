# workbench-git

Git identity and multi-context project management for the
[`workbench`](https://github.com/GingerGraham/workbench-core) ecosystem.

An **ecosystem module** (`workbench-core` ARCHITECTURE.md §2). Requires
`workbench-core` only — it works without any other workbench module (see
"Using workbench-git on its own" below):

```sh
wb add git
# or, as part of a bundle:
wb install --bundle workstation
```

## What this gives you

- Git aliases and helpers (`gwt`/`gwt-cd` worktree helpers, `git-cleanup`,
  `gitgraph`, and the usual short aliases — `gst`, `gco`, `gcm`, ...).
- **Multi-context project identity**: commit author/email and GPG signing
  key follow the working directory automatically, keyed by
  `<context>/<provider>` (e.g. `Personal/GitHub`, `Acme/AzureDevOps`) via
  git's `includeIf`.
- **CLI context wiring** (optional, per-project): gives a project tree its
  own `gh`/`glab` config directory and credential helper, activated by
  `direnv` on `cd` — so `gh`/`glab` authentication follows the working
  directory the same way identity already does. Useful for a personal vs.
  work account on the same provider, or several concurrent client accounts.
- Installers for `gh`, `glab` and `yq` — `wb tools install <name>` (see
  `shell/installers.sh`).

## Getting started

```sh
wb add git
wb tools install yq           # one tool per call; also gh, glab. 'wb tools install all' asks first
git-setup-identity            # interactive: name, email, editor, signing key
git-add-project Personal GitHub me@example.com
```

## File ownership

| File | Managed by | Notes |
|------|-----------|-------|
| `~/.gitconfig` (`user.*`, `core.editor`, `diff.tool`, `merge.tool`) | You, or `git-setup-identity` (interactive) | Never touched by sync |
| `~/.gitconfig` (two workbench blocks) | `workbench-core`, from this module's `layers:` | A workbench block (layer) at the top, including `files/gitconfig` (defaults), and one at the end, including `files/gitconfig-contexts` (`profiles/local.inc` and `project-includes`). Your content outside the blocks is never touched, and anything you set there wins over the defaults. `wb files status` lists them |
| `~/.local/share/workbench/modules/git/files/attributes`, `.../ignore` | This module's `deploy:` entries | Re-deployed (force) on every sync. **Not** `~/.config/git/` — see note below |
| `~/.config/git/projects.yml` | Created by `git-add-project` on first use, then the shell functions | Live source of truth — never overwritten after creation |
| `~/.config/git/project-includes` | Regenerated by the shell functions on every add/update/remove | Absent until your first project — git ignores a missing include |
| `~/.config/git/profiles/<n>.inc` | Shell functions, on first `git-add-project` for that context/provider | User-editable after creation |
| `~/.config/git/profiles/local.inc` | User only | Create it yourself for machine-local overrides (credential helpers, WIP settings); included from the end of `~/.gitconfig`, so it wins everywhere |
| `~/.config/direnv/lib/workbench-git-context.sh` | This module's `deploy:` entries | Re-deployed (force) on every sync, no user content |
| `~/.config/git/<gh\|glab>/<context-slug>/` | Shell functions | Directory only — contents owned by `gh`/`glab` |
| `<projects_base>/<context>/<provider>/.envrc` | Shell functions | Generated, only for projects with `cli` set |
| `<projects_base>/<context>/<provider>/.envrc.local` | User only | Sourced by the generated `.envrc`, never touched |

**Why `attributes`/`ignore` don't live in `~/.config/git/`:** that prefix is
on `workbench-core`'s `deploy[].dest` denylist
([`contracts/manifest-spec.md`](https://github.com/GingerGraham/workbench-core/blob/main/contracts/manifest-spec.md#dest-validation))
— a deliberate trust boundary, not an oversight, and not specific to this
module. `core.excludesfile`/`core.attributesfile` don't have to point at
`~/.config/git/` for git to honour them, so `files/gitconfig` points them
at the files' actual, engine-managed deploy location under
`~/.local/share/workbench/modules/git/files/`. Everything else in this
table that *does* live under `~/.config/git/` (`projects.yml`,
`project-includes`, `profiles/`) is generated there at runtime by this
module's shell functions, not by a `deploy:` entry — the denylist only
constrains `deploy:` destinations, so that placement is unaffected.

**Upgrading from a version with the post-deploy hook:** the hook wrote
`core.excludesfile`, `core.attributesfile` and two `include.path` lines
straight into your `~/.gitconfig`. On the first update with layers,
`workbench-core` backs your `~/.gitconfig` up, removes exactly those lines
(`files/legacy/gitconfig-hook`), and adds the two blocks in their place.
Anything that doesn't match exactly is left alone, with a warning naming
the line.

## Using workbench-git on its own

- **Needs `workbench-core` only.** No other workbench module, and no
  `--allow-hooks`: this module ships no hook.
- **Your `~/.gitconfig` stays yours.** `wb add git` adds two marked blocks
  to it; everything you set outside them wins. If you'd rather not have
  workbench-git's defaults at all: `wb files policy git gitconfig skip`
  (or `wb add git --skip-layer gitconfig`). The project-contexts block is
  `gitconfig:over`.
- **direnv** is needed only for CLI contexts (`git-add-project-cli`), and
  any install of it works — your package manager, or `wb tools install
  direnv` with `workbench-shell` registered. If nothing else has hooked
  direnv into your shell, this module hooks it itself once you have a CLI
  context.
- **workbench-gpg** is optional: with it, a GPG key you pass is resolved
  to its signing subkey (see below).

**Deliberate simplification from `workbench-precursor`:** the donor codebase
also mirrored every manifest change into Ansible's `host_vars/localhost.yml`
so a later Ansible re-run stayed convergent. `workbench-core` has no
equivalent host_vars concept — `projects.yml` is the *only* source of truth
here.

## CLI context

`gh`/`glab` each hold one global credential set, so switching between a
personal and a work account (same provider) normally means switching
credentials by hand — `git-add-project`'s identity wiring alone doesn't
help, since identity and authentication are different things.

CLI context wiring closes that gap using the same working-directory trick,
via `direnv`: setting a project's `cli` field gives it its own `gh`/`glab`
config directory, a generated `.envrc` that activates it on `cd`, and a
credential helper scoped to that project tree.

```
use git_context <gh|glab> <context-slug> [host]
```

is the one-line `.envrc` contract, backed by
`~/.config/direnv/lib/workbench-git-context.sh` (deployed by this module).
It sets `GH_CONFIG_DIR`/`GLAB_CONFIG_DIR` (and `GH_HOST`/`GITLAB_HOST` for a
non-default host), and can, for `gh`, re-export `GITHUB_PERSONAL_ACCESS_TOKEN`
from that context's own `gh auth token` (a local keyring read, no network
call).

That export is **opt-in, off by default**: an exported token is readable by
every process the shell starts — build tools, test runners, npm lifecycle
scripts, AI agents — and a `gh` OAuth token typically carries `repo` and
`workflow` scope, the account's full reach. Enable it with

```sh
export WORKBENCH_GIT_CONTEXT_EXPORT_TOKEN=true
```

in `~/.config/workbench/local/settings.sh` (it must be `export`ed — direnv
evaluates `.envrc` in a child bash process). This also gates the same
eager, out-of-tree export in `shell/git.sh`. Prefer passing the token to the
one tool that needs it at launch instead, when you can:

```sh
GITHUB_PERSONAL_ACCESS_TOKEN="$(gh auth token)" <tool>
```

This is wiring only — you still run `gh auth login`/`glab auth login`
yourself.

workbench-git runs `direnv allow` on the `.envrc` each time it writes one
(or finds it unchanged), so the context is active the first time you `cd`
in. Before that it checks the values going into the file: the context
slug must use only `a-z 0-9 . _ -`, the CLI must be `gh` or `glab`, and a
host must be a hostname with an optional `:port`. The generated `.envrc`
sources `.envrc.local` when it exists, and direnv only checks the root
`.envrc` before trusting it, so anything you put in `.envrc.local` runs
once the generated file is allowed.

direnv reads its lib from `${XDG_CONFIG_HOME:-~/.config}/direnv/lib`, so
with `XDG_CONFIG_HOME` set elsewhere, wiring a project warns and prints the
`ln -s` that makes the file visible there.

```sh
git-add-project-cli <context> <provider> [--cli gh|glab] [--host <hostname>] [--adopt <path>]
git-update-project <context> <provider> --cli <gh|glab|none> [--cli-host <hostname>]
git-remove-project-cli <context> <provider>
```

`--adopt <path>` (or the automatic adopt-candidate probe, when stdin is a
TTY and the target config dir is still empty) copies an existing
`hosts.yml`/`config.yml` into the new context directory instead of
re-running `auth login` — never moves or deletes the source, never
overwrites a non-empty target.

**Known limitation:** the credential helper invokes `gh`/`glab`, which reads
`GH_CONFIG_DIR`/`GLAB_CONFIG_DIR` from its environment — a git operation
launched from a process that didn't inherit direnv's environment (some IDE
integrations, some daemons) falls back to the default, unscoped credential
store.

Out of scope: SSH-based auth, Windows/PowerShell, and context-aware
`gpg-push-github`/`gpg-push-gitlab` (they use the ambient CLI config today).

## Shell functions

### Project management

```sh
git-add-project <context> <provider> <email> [signing-key] [name] [--no-cli]
git-update-project <context> <provider> [--email <e>] [--signing-key <k>] [--name <n>] [--cli <gh|glab|none>] [--cli-host <hostname>]
git-remove-project <context> <provider>
git-list-projects
git-sync-projects [--status]
git-projects-base
```

### CLI wiring

```sh
git-add-project-cli <context> <provider> [--cli gh|glab] [--host <hostname>] [--adopt <path>]
git-remove-project-cli <context> <provider>
```

### Identity setup

```sh
git-setup-identity   # interactive; safe to re-run
```

Writes only the values you enter (name, email, editor, diff/merge tool,
signing key). If you have no `[user]` section yet, git appends one at the
end of `~/.gitconfig`; `git-setup-identity` then puts the project-contexts
block back after it, so per-project identities still win inside each
project.

If you have no identity set yet, run this once after `wb add git`.

## Soft dependency on workbench-gpg

`git-setup-identity`, `git-add-project` and `git-update-project
--signing-key` resolve a GPG master key/fingerprint to its `[S]` signing
subkey via `gpg-resolve-signing-key` (`workbench-gpg`'s public function for
other modules), when both `gpg` and that function are present. Without
`workbench-gpg` installed, a signing key you pass is used as-is (no
subkey resolution) — this is a soft dependency, not a hard `core_api:` one.

Signing is turned on (`commit.gpgsign`, `tag.gpgsign`) only when `gpg` is
installed. Without it the key is still saved, signing is left off so
commits keep working, and you get a warning; install gnupg and re-run the
same command to turn it on.

## Installers (`wb tools`)

`wb tools install gh`, `wb tools install glab`, `wb tools install yq` — see
[`docs/module-authoring.md`](https://github.com/GingerGraham/workbench-core/blob/main/docs/module-authoring.md#declaring-installers-wb-tools)
in `workbench-core` for how `wb tools` discovers and invokes these.

## Requires

- `yq` v4 ([mikefarah/yq](https://github.com/mikefarah/yq)) for manifest
  operations — `wb tools install yq` installs it.
  Without a working `yq`, `get-git-functions` lists the project-management
  functions under "available once tooling is installed", with the
  requirement and the install command. They are still defined; running one
  prints the specific error. `WORKBENCH_FUNCTIONS_SHOW_ALL=true
  get-git-functions` shows everything as available.
- `direnv`, only if you use CLI context wiring (`workbench-shell` provides
  `wb tools install direnv`).
- `gh` or `glab`, only for CLI context wiring. Until the project's CLI is
  installed, its credential helper isn't written (git would have no
  helper); install it, then run `git-sync-projects`.
