# workbench-git

Git identity and multi-context project management for the
[`workbench`](https://github.com/GingerGraham/workbench-core) ecosystem.

An **ecosystem module** (`workbench-core` ARCHITECTURE.md §2) — meaningless
standalone. Requires `workbench-core` installed first:

```sh
wb add git
# or, as part of a bundle:
wb install --bundle workstation
```

## What this gives you

- Git aliases and helpers (`gwt`/`gwt-cd` worktree helpers, `git-cleanup`,
  `gitgraph`, and the usual short aliases — `gst`, `gco`, `gcm`, ...).
- **Multi-context project identity**: commit author/email and GPG signing
  key follow the working directory automatically, keyed by
  `<context>/<provider>` (e.g. `Personal/GitHub`, `Acme/AzureDevOps`) via
  git's `includeIf`.
- **CLI context wiring** (optional, per-project): gives a project tree its
  own `gh`/`glab` config directory and credential helper, activated by
  `direnv` on `cd` — so `gh`/`glab` authentication follows the working
  directory the same way identity already does. Useful for a personal vs.
  work account on the same provider, or several concurrent client accounts.
- `install-gh`, `install-glab`, `install-yq` — via `wb tools update` (see
  `shell/installers.sh`).

## Getting started

```sh
wb add git
wb tools update yq gh glab   # or: wb tools update (installs everything registered)
git-setup-identity            # interactive: name, email, editor, signing key
git-add-project Personal GitHub me@example.com
```

## File ownership

| File | Managed by | Notes |
|------|-----------|-------|
| `~/.gitconfig` (`user.*`, `core.editor`, `diff.tool`, `merge.tool`) | `git-setup-identity`, interactive | Never touched by sync — this is the one thing no hook can safely guess |
| `~/.gitconfig` (`core.excludesfile`/`attributesfile`/`include.path`) | `hooks/post-deploy.sh`, once | Re-run safely via `wb update git` if ever needed |
| `~/.config/git/attributes`, `~/.config/git/ignore` | This module's `deploy:` entries | Re-deployed (force) on every sync |
| `~/.config/git/projects.yml` | `hooks/post-deploy.sh` (first run only) then the shell functions | Live source of truth — never overwritten after creation |
| `~/.config/git/project-includes` | `hooks/post-deploy.sh` (first run) then regenerated by the shell functions on every add/update/remove | |
| `~/.config/git/profiles/<n>.inc` | Shell functions, on first `git-add-project` for that context/provider | User-editable after creation |
| `~/.config/git/profiles/local.inc` | User only | Never touched after creation — machine-local overrides (credential helpers, WIP settings) |
| `~/.config/direnv/lib/workbench-git-context.sh` | This module's `deploy:` entries | Re-deployed (force) on every sync, no user content |
| `~/.config/git/<gh\|glab>/<context-slug>/` | Shell functions | Directory only — contents owned by `gh`/`glab` |
| `<projects_base>/<context>/<provider>/.envrc` | Shell functions | Generated, only for projects with `cli` set |
| `<projects_base>/<context>/<provider>/.envrc.local` | User only | Sourced by the generated `.envrc`, never touched |

**Deliberate simplification from `workbench-precursor`:** the donor codebase
also mirrored every manifest change into Ansible's `host_vars/localhost.yml`
so a later Ansible re-run stayed convergent. `workbench-core` has no
equivalent host_vars concept — `projects.yml` is the *only* source of truth
here.

## CLI context

`gh`/`glab` each hold one global credential set, so switching between a
personal and a work account (same provider) normally means switching
credentials by hand — `git-add-project`'s identity wiring alone doesn't
help, since identity and authentication are different things.

CLI context wiring closes that gap using the same working-directory trick,
via `direnv`: setting a project's `cli` field gives it its own `gh`/`glab`
config directory, a generated `.envrc` that activates it on `cd`, and a
credential helper scoped to that project tree.

```
use git_context <gh|glab> <context-slug> [host]
```

is the one-line `.envrc` contract, backed by
`~/.config/direnv/lib/workbench-git-context.sh` (deployed by this module).
It sets `GH_CONFIG_DIR`/`GLAB_CONFIG_DIR` (and `GH_HOST`/`GITLAB_HOST` for a
non-default host), and for `gh`, re-exports `GITHUB_PERSONAL_ACCESS_TOKEN`
from that context's own `gh auth token` (a local keyring read, no network
call) — opt out with `WORKBENCH_GIT_CONTEXT_EXPORT_TOKEN=false` in
`~/.config/workbench/local/settings.sh`.

This is wiring only — you still run `gh auth login`/`glab auth login`
yourself.

```sh
git-add-project-cli <context> <provider> [--cli gh|glab] [--host <hostname>] [--adopt <path>]
git-update-project <context> <provider> --cli <gh|glab|none> [--cli-host <hostname>]
git-remove-project-cli <context> <provider>
```

`--adopt <path>` (or the automatic adopt-candidate probe, when stdin is a
TTY and the target config dir is still empty) copies an existing
`hosts.yml`/`config.yml` into the new context directory instead of
re-running `auth login` — never moves or deletes the source, never
overwrites a non-empty target.

**Known limitation:** the credential helper invokes `gh`/`glab`, which reads
`GH_CONFIG_DIR`/`GLAB_CONFIG_DIR` from its environment — a git operation
launched from a process that didn't inherit direnv's environment (some IDE
integrations, some daemons) falls back to the default, unscoped credential
store.

Out of scope: SSH-based auth, Windows/PowerShell, and context-aware
`gpg-push-github`/`gpg-push-gitlab` (they use the ambient CLI config today).

## Shell functions

### Project management

```sh
git-add-project <context> <provider> <email> [signing-key] [name] [--no-cli]
git-update-project <context> <provider> [--email <e>] [--signing-key <k>] [--name <n>] [--cli <gh|glab|none>] [--cli-host <hostname>]
git-remove-project <context> <provider>
git-list-projects
git-sync-projects [--status]
git-projects-base
```

### CLI wiring

```sh
git-add-project-cli <context> <provider> [--cli gh|glab] [--host <hostname>] [--adopt <path>]
git-remove-project-cli <context> <provider>
```

### Identity setup

```sh
git-setup-identity   # interactive; safe to re-run
```

## Soft dependency on workbench-gpg

`git-add-project`/`git-update-project --signing-key` resolve a GPG master
key/fingerprint to its `[S]` signing subkey via `_gpg_resolve_signing_key`
(`workbench-gpg`), when both `gpg` and that function are present. Without
`workbench-gpg` installed, a signing key you pass is used as-is (no
subkey resolution) — this is a soft dependency, not a hard `core_api:` one.
